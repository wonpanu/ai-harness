Backend · skill go-backend-style

Guard clause + early return — ไม่มี else

Error handling อ่านเป็น ladder แบนของ if guard อิสระ แต่ละอัน return ออกทันที — ในโค้ดเขียนมือของ repo อ้างอิงไม่มี } else { เลยแม้แต่จุดเดียว

อย่าทำ — nested 
func (r *repo) GetOrder(ctx ..., id string) {
    resp, err := r.client.Get(url)
    if err == nil {
        if resp.StatusCode() == 200 {
            if resp.Body != nil {
                return resp.ToEntity(), nil
            } else {
                return nil, errEmptyBody
            }
        } else { ... }
    } else { ... }
}
ทำแบบนี้ — flat ladder 
func (r *repo) GetOrder(ctx ..., id string) {
    resp, err := r.client.Get(url)
    if err != nil {
        return nil, errs.New(errcode.OrderFetchFailed, err)
    }
    if resp.StatusCode() == 404 {
        return nil, errs.New(errcode.OrderNotFound, err)
    }
    if resp.Body == nil {
        return nil, errs.New(errcode.OrderEmptyBody, err)
    }
    return resp.ToEntity(), nil
}

ชื่อสื่อความหมาย ไม่ย่อ — แม้จะยาว

โค้ดต้องอ่านรู้เรื่องโดยไม่พึ่ง comment ชื่อสั้นใช้ได้เฉพาะ scope แคบ: ตัวแปร loop และ receiver ตัวอักษรเดียว (h handler, u usecase, r repo)

อย่าทำ 
type refundsUsecase struct {
    maxAmt float64
    gwBase string
}
ทำแบบนี้ 
type refundsUsecase struct {
    maximumRefundAmount    float64
    paymentGatewayBaseURL  string
}

คำนวณ boolean ตั้งชื่อไว้ก่อน แล้ว branch จากชื่อ

ชื่อทำหน้าที่อธิบาย intent ในตัว และเงื่อนไขถูกทดสอบครั้งเดียว ไม่ต้องเขียนซ้ำ inline ทุก branch

อย่าทำ 
if order.Type != nil && *order.Type == "express" {
    order.Queue = expressQueue
}
...
if order.Type != nil && *order.Type == "express" {
    span.SetAttributes(...)
}
ทำแบบนี้ 
isExpress := order.Type != nil &&
    *order.Type == "express"

if isExpress {
    order.Queue = expressQueue
}
...
if isExpress { span.SetAttributes(...) }

Comment อธิบาย why ไม่ใช่ what

เขียนเหตุผล workaround หรือ constraint ที่โค้ดแสดงเองไม่ได้ เป็นประโยคสั้นตัวพิมพ์เล็ก — godoc เฉพาะ exported symbol ที่กฎไม่ได้อยู่ใน signature

อย่าทำ 
// loop over accounts
for _, a := range accounts {
    // append to result
    result = append(result, a.ToEntity())
}
ทำแบบนี้ 
// express orders skip the nightly batch; route them
// to the priority queue so same-day delivery holds
if isExpress {
    order.Queue = expressQueue
}

ที่เหลือยึด official style ของภาษา

Go บังคับ initialism casing: ID, URL, API — ข้อยกเว้นเดียวคือ struct ที่ mirror wire format ให้ใช้ casing ตาม JSON ต้นทางเป๊ะ

อย่าทำ 
type Account struct {
    UserId              string
    ProfileImageUrl     string
    ApiKeyExpireAt      time.Time
}
ทำแบบนี้ 
type Account struct {
    UserID               string
    UserProfileImageURL  string
    APIKeyExpireAt       time.Time
}

Frontend · skill react-frontend-style (+ tailwindcss-style, tanstack-query-style)

กลั่นจาก pattern ที่ทำสม่ำเสมอใน production React app

Component

หนึ่ง component ต่อไฟล์ ชื่อไฟล์ PascalCase = ชื่อ component · orchestrator ทำหน้าที่ compose hook + render, pure UI อยู่ใน components/ · ไม่มี barrel index.ts — import path ตรง

Hooks

useXxx ไฟล์ละตัว · return object ที่ตั้งชื่อค่าแต่ละตัว ไม่ส่ง raw library result ออกไป · expose handler (handleX) ไม่ใช่ raw setter · derived flag คำนวณใน hook ไม่ใช่ใน JSX

State

State ที่เกี่ยวกันรวมเป็น object เดียว + patch updater เดียว · UI mode ที่ exclusive กันใช้ discriminated union เดียว ไม่ใช่ boolean หลายตัว · derive ได้อย่า store ซ้ำ · Context เฉพาะ state ที่ลึก ≥3 ชั้น (memoized + hook ที่ throw เมื่อไม่มี provider)

Rendering

Loading/error/empty เป็น early-return ladder ใน gate component ที่คืน pure content component · inline && ใช้แค่ JSX ชิ้นเล็ก optional ไม่ใช่ state branching

TypeScript

interface สำหรับ shape, type สำหรับ union/derived · import type เสมอ · ไม่มี any ใน app code · string-literal set เป็น as const แล้ว derive type · เปิด compiler config เข้มสุดที่โปรเจกต์รับได้

Naming

Handler = handleX, callback prop = onX, boolean = is/has/should/can · props interface ชื่อ <Component>Props วางเหนือ component

Data layer

Wire type → domain entity ผ่าน pure mapper → service · HTTP client typed ตัวเดียวร่วมกัน feature ห้ามเรียก fetch เอง · service เป็น injectable factory คืน mapped entity — consumer ไม่แตะ wire envelope

Styling & tests

Conditional class ผ่าน cn() helper · ใช้ semantic design token แทน raw palette · logic ที่ต้องพึ่ง DOM แยกเป็น pure function แล้ว test ตรงนั้น hook เป็นแค่ thin binding

Session mode · /fable-mode

Fable mode

โครง discipline ระดับ frontier model สำหรับ model ที่เบากว่า (เช่น Opus 5) — เพิ่ม raw capability ไม่ได้ แต่บังคับ habit ที่ model ระดับท็อปทำเองโดยธรรมชาติ เรียกใช้เองเท่านั้น มีผลจนสั่ง "stop fable mode"

1ก่อนลงมือ

Restate โจทย์หนึ่งบรรทัด ไล่ assumption ที่รับน้ำหนัก — อะไร verify ได้ต้องอ่านจริง ห้ามตอบจากความจำ ชั่งน้ำหนัก 2-3 approach ก่อน commit

2ระหว่างทำ

พยายาม falsify ทุกข้อสรุปสำคัญ ผลที่ surprise คือ signal — หยุดแล้ว reconcile ก่อนต่อยอด ทำ step เล็ก ตามด้วย check ที่ถูกสุดที่จะ fail ถ้าผิด

3ก่อน claim ว่าเสร็จ

Self-review แบบ hostile reviewer ทุก claim ต้อง verified, cite file:line หรือ label ว่า unverified — รัน check จริง ไม่ใช่ proxy

4Escalation

ยังไม่แน่ใจ → fan out ไป deep-reasoner + peer ตัวใหม่คู่ขนานแล้วสังเคราะห์ สองคำตอบขัดกันโดยไม่มีหลักฐานตัดสิน → เสนอทั้งคู่พร้อม deciding experiment

5Calibration

เรื่องที่ verify แล้วพูดตรง ๆ ไม่ hedge เรื่องเดา label ว่าเดา ผิดก่อนหน้าต้องแก้ให้ชัดเจน

Checklist ที่ agent ต้อง copy ลง response แล้วติ๊กตามจริง (ข้ามได้เฉพาะงาน trivial): 
Fable checklist:
- [ ] Problem restated; load-bearing assumptions read, not recalled
- [ ] 2-3 approaches weighed before committing
- [ ] Each significant conclusion challenged (falsify pass)
- [ ] Cheapest failing check run after each step
- [ ] Hostile self-review of final diff/answer
- [ ] Every claim: verified, cited file:line, or labeled unverified
- [ ] Real check run (tests/app), not a proxy

Skill · /creating-skills

Creating skills

คู่มือสร้าง/ปรับโครงสร้าง skill ตาม best practices ล่าสุดของ Anthropic — เลือก pattern ให้ตรง use case และบังคับ fetch doc จริงก่อน finalize ทุกครั้งกันของค้างเก่า

Degrees of freedom

งานยืดหยุ่นหลายทาง → heuristic prose · งานมี pattern ที่ชอบ → template/pseudocode · งานเปราะ (migration, destructive) → สคริปต์เป๊ะ ห้ามเพิ่ม flag

Structure

ไฟล์เดียวจนใกล้ 500 บรรทัด → แยก reference ลึก 1 ชั้นเท่านั้น · หลาย domain → ไฟล์ละ domain โหลดเฉพาะที่เกี่ยว · basic vs advanced → conditional link

Reliability

หลายขั้นตอน → copyable checklist · คุณภาพสำคัญ → feedback loop (draft → validate → fix) · format สำคัญ → template · งาน style → example pairs · งาน destructive → plan-validate-execute

Scripts

Solve ไม่ defer error ให้ Claude · ห้าม voodoo constant ทุกค่าต้องมีเหตุผล · บอกชัดว่า execute ("Run x.py") หรือ read ("See x.py") · ระบุ package ที่ต้องมี

Process

Eval-first: ทำงานจริงโดยไม่มี skill ก่อนเพื่อเก็บ gap → เขียน minimal ให้ผ่าน eval → test ด้วย fresh instance ทุก model tier → observe การใช้จริงแล้วปรับ → เช็ค live checklist ก่อน ship

General practice

กฎการทำงาน

PRD ก่อนลงมือ

ทุก requirement ที่เข้ามาต้องมี PRD ย่อ — goal, acceptance criteria, context ที่จำเป็น — ส่งให้ทุก worker และ reviewer ที่ delegate งานเล็กไม่กี่บรรทัดพอ งานใหญ่ค่อยเต็มรูป ถ้า domain term ใน requirement กำกวมหรือความหมายอาจต่างใน context ของโปรเจกต์ → รัน grill-with-docs ก่อนร่าง PRD เพื่อเทียบศัพท์กับ domain model/docs ให้ตรงก่อน

Docs-first

ยึด practice ที่ถูกที่สุดแม้ขัด convention ปัจจุบัน — การเปลี่ยน pattern ต้องเสนอและแก้ docs ก่อนลงมือ implement

Pattern ไม่ใช่ copy

Reference repo ให้ pattern (state management, hook structure, return shape) — ตั้งชื่อใหม่ทั้งหมดให้สื่อหน้าที่ใน repo ของเราเอง

Verify ไม่ใช่จำ

ก่อน assert ว่า "ส่วนอื่นถูก practice แล้ว" ต้อง explore โค้ดจริง อย่าเชื่อความจำ

Grill ก่อนเริ่ม

Challenge สมมติฐานผ่าน AskUserQuestion ทีละคำถามก่อนเริ่มงาน เคาะ decision เป็นข้อ ๆ
